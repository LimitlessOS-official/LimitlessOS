# LimitlessOS Security Model

## Security priorities

- verified boot
- least privilege
- memory safety where possible
- explicit consent for AI actions
- clear auditability
- graceful failure instead of hidden escalation

## Threat model

LimitlessOS is designed to resist:

- commodity malware
- malicious apps in user space
- compromised third-party drivers
- lateral movement between services
- accidental privilege misuse by automation

It is not honest to claim that any system is impossible to hack. Physical attackers, vulnerable firmware, malicious hardware, or stolen signing keys can still create risk. The goal is to make compromise difficult, visible, and containable.

## AI assistant boundary

The user's requirement was that the AI assistant cannot be edited, viewed, or hacked. A realistic interpretation is:

- users may interact with the assistant UI and settings
- users may not alter the signed assistant core or policy engine
- the assistant core runs in a protected system partition or isolated trust domain
- sensitive model weights and policy logic stay server-side or in encrypted sealed storage
- every high-risk action requires user approval or a narrowly scoped standing permission

## Consent model

The assistant can classify actions into levels:

- level 0: read-only help and explanation
- level 1: reversible local changes with one-time consent
- level 2: privileged system changes with explicit confirmation and logged rationale
- level 3: blocked by default unless enterprise or developer policy enables the workflow
- level 4: allow everything with a one-time prompt for consent lasting the entire session/chat

If a user denies a request, the assistant must:

- explain why it asked
- offer a manual path
- avoid repeated nagging
- only re-prompt when context changed materially

## Hardening direction

- signed kernel and service binaries
- measured launch for privileged services
- code integrity enforcement for the assistant broker
- remote attestation for cloud-backed AI actions
- per-service capabilities instead of broad admin tokens
- tamper-evident audit logs
- crash-only restart for user-space services to reduce persistence

Current bootstrap implementation direction:

- service identity is bound to scheduled kernel work, not just to caller-supplied metadata
- IPC endpoints can require explicit service capabilities
- denied privileged routing attempts are counted and surfaced to telemetry
- the AI policy broker is treated as a guarded endpoint instead of a normal unrestricted queue
- kernel-to-user transitions use a dedicated TSS-backed ring transition path instead of sharing a flat in-kernel execution context
- bootstrap user processes now run in separate page directories with dedicated user code and stack mappings
- timer interrupts can now preempt a running user task and resume another saved user frame under kernel control
- bootstrap user processes can now block on kernel-managed mailbox replies instead of polling blindly for privileged policy outcomes
- direct user-to-user mailbox sends now copy bounded payload buffers through kernel-validated user memory and are checked against per-endpoint sender rules before delivery
- ring-3 receivers must now explicitly register their endpoints before they can be targeted, which narrows the accidental-ambient attack surface for early user IPC
- endpoint discovery now resolves by owner and declared role instead of assuming one fixed inbox per process, reducing implicit addressing shortcuts in early user IPC
- bootstrap services and ring-3 policy clients now resolve the AI broker through a kernel-controlled service namespace instead of baking in a privileged endpoint number
- ring-3 sends now consume process-scoped capability handles issued by lookup syscalls instead of sending directly to raw destination endpoint IDs
- capability handles can now be explicitly revoked, and stale handles are rejected rather than silently becoming valid again after a later lookup
- ring-3 endpoints can now publish explicit class identifiers, and peer processes resolve those classes through the kernel before receiving a capability grant to send
- capability delegation can now transfer a narrower send right to another ring-3 process through a kernel-mediated mailbox delivery, instead of requiring every client to resolve every target directly
- delegated capabilities now carry provenance about the issuing process and are attenuated to send-only rights, so a receiver cannot automatically re-delegate a borrowed authority
- delegation now also obeys endpoint policy: privileged services or user endpoints must explicitly opt in to being delegable, and non-delegable sources are blocked even if a caller still has a locally delegable handle
- delegated capabilities now carry bounded leases and expire automatically on PIT ticks, so borrowed authority times out even if the receiver never explicitly revokes it
- process discovery is now profile-scoped before capability issuance: a sandboxed task can be denied service-class or endpoint-class discovery even when the target endpoint itself would otherwise accept that sender
- ring-3 scheduling now also honors explicit per-process policy: interactive tasks can receive higher weight and tighter latency targets, while sandboxed work can be de-prioritized without blocking it forever because overdue latency targets still force eventual selection
- IPC wakeups now feed into the same policy boundary: an interactive ring-3 task can receive a short kernel-managed dispatch deadline when brokered I/O completes, while sandboxed workers do not inherit the same responsiveness boost by default
- per-class CPU budgets now bound how much uninterrupted compute a scheduling class can consume inside a budget window, so a busy interactive client cannot starve sandboxed work indefinitely once its immediate deadlines have been met
- brokered policy paths now have inversion-aware urgent wakes: when an interactive task is blocked on the AI-policy broker, the kernel marks that broker wake as urgent so the dependency is serviced ahead of ordinary kernel work
- capability admission is now pressure-aware: each ring-3 profile has a bounded number of concurrent capability slots it may hold before new grants are denied, which limits authority fan-out under load
- broker IPC now carries explicit dependency depth and rejects over-depth chained replies, so future multi-broker workflows have a bounded kernel-enforced graph depth instead of unbounded implicit forwarding
- capability tables now compact after revokes and expirations, and duplicate grants reuse an existing handle instead of spraying new authority slots, which keeps bootstrap handle pressure predictable under repeated lookups and leased delegation churn
- the AI-policy broker now applies explicit backpressure to bursty non-interactive clients and exposes queue high-water plus route-graph telemetry, so service-graph pressure becomes visible and rate-limited instead of turning into silent queue growth
- executable launch is now mediated by a kernel-owned bootstrap manifest catalog and `init`, not by hard-wired entry into pre-created launch slots, which gives the trusted core one place to verify measured image metadata, enforce launch authority and instance caps, and attach profile, scheduler, and authority policy to a spawned user-space service before it ever runs
- bootstrap package intake now has a signer trust gate before launch time: the kernel parses a generated serialized archive, validates its structure and checksum, accepts only candidates whose signer policy and manifest envelope match the trusted signer registry, and rejects untrusted candidates before they can enter the runnable catalog

M8 exposes this trust state through read-only Settings and `pkginfo` telemetry only: those surfaces receive no install capability, update-apply capability, filesystem write authority, raw network authority, raw package mutation authority, or boot-entry authority. Live public update fetching, auto-install, app-store behavior, and package apply/install actions remain unavailable/non-product, and signature expiry is not Product-enforced without trusted time.

- the x64 launch-broker image-map proof now records a protection profile and token for the mapped transfer image, and the accepted validation profile explicitly requires `user 0`, `writable 0`, `supervisor-only 1`, and `validation-only 1`; the broker then installs a distinct user executable view with `user 1`, `writable 0`, `supervisor-only 0`, and `validation-only 0` instead of silently widening the validation mapping

## Offline and privacy behavior

Cloud assistance should improve the system, not control it. When offline:

- core OS features remain fully usable
- local assistant features continue with reduced capability
- no hidden data buffering for upload without consent
- any memory sync waits for network return and explicit policy allowance
